# Audit — simplicity, flow, duplicates, assistant, support access (Oct 2026)

Scope: the whole app, read with five goals in mind — simple flows, clear
functions and structure, no duplicate users, a deterministic in-app
assistant, and an agent/support person able to run a group from the
backend. Every finding below cites the code it comes from. Nothing here is
built yet; section 8 is the suggested order.

Checks at the time of writing: `tsc` clean, `eslint` clean, 211/211 unit
tests pass, the two DB-backed suites need a database and were not run.

---

## 1. Verdict

The foundations are strong: tenant isolation (RLS + explicit `group_id`
filters), pure tested business rules in `lib/domain/*`, one nav config,
good docs. The problems are in the **seams between features**:

1. **The same person can easily become two or three users** (section 3).
2. **Setting up a new group has a dead end** — the founder cannot get a
   Treasurer and Secretary in without typing passwords for them, and it
   breaks for anyone who already has an account (section 2).
3. **Business logic lives inside UI handlers**, so the API, a support
   person or an agent cannot reuse it, and copies have already drifted
   (section 4).
4. **Support staff cannot act inside a group at all.** The only tool they
   have — resetting a password — signs the user out and takes their
   password away (section 5).
5. **The recommendation engine is already deterministic** and is the right
   base for the assistant, but it has no buttons and lives only on the
   Insights page (section 6).

## 2. Example flow: Wanjiku starts "Umoja Women Group"

Walked through the code path by path.

| # | Step | Code | Result |
|---|---|---|---|
| 1 | Registers with phone `0712345678` | `registerAction` (`app/(auth)/actions.ts`) | ✅ Works. But no check whether that phone already has an account. |
| 2 | Empty dashboard → **Start a group** | `app/(dashboard)/dashboard/page.tsx` → `/dashboard/onboarding` | ✅ Clear. |
| 3 | Fills in group details | `createOnboardingGroupAction` — lives in `app/super-admin/groups/actions.ts` even though any user calls it | ✅ Works; she is admin. ⚠️ The file location is misleading. |
| 4 | Banner: "assign a Treasurer and Secretary" | `generateRecommendations` / Home banner | ✅ Clear message, but no button that does it. |
| 5 | Wants Akinyi (who already uses the app in another chama) as Treasurer | — | ❌ **Dead end.** Akinyi cannot request to join: `requestToJoinAction` and `/discover/[id]` require `registrationComplete = true`, which needs a Treasurer. Chicken and egg. |
| 6 | Workaround: Members → Add member "Akinyi" | `createMemberAction` | ⚠️ Creates a roster row with no login. No check for an existing person with that phone. |
| 7 | More details → Create login for Akinyi | `createLoginForMemberAction` | ❌ If she enters Akinyi's email: error "account already exists", and no way to link. If she enters the phone: **a second user for Akinyi is created**, and Wanjiku now knows Akinyi's password. |
| 8 | Change Akinyi's role to Treasurer | `updateMemberRoleAction` | ✅ Works once a login exists. |
| 9 | Same for the Secretary | — | Same problems as 5–8. |
| 10 | Group now complete; shares link to `/discover` | `app/(public)/discover/page.tsx` | ❌ The group does not appear: `/discover` is built once at deploy time and only super-admin actions refresh it. |
| 11 | Members request to join and get approved | `approveMembershipAction` | ⚠️ If staff had already added that person by hand in step 6 style, approval creates a **second `members` row** for them (lookup is by `userId` only). |
| 12 | "Requests are approved quickly" shown on Discover | `requireApproval` | ⚠️ Setting is shown but never enforced — every request waits for approval anyway. |
| 13 | Wanjiku (admin) wants a loan herself | nav `My Loan` is `roles: ["member"]` | ⚠️ Officials never see the apply link (the page itself allows them). |
| 14 | Akinyi (treasurer) applies and approves her own loan | `reviewApplicationAction` | ❌ Allowed. Welfare blocks self-approval (`welfare/actions.ts:336`); loans do not. |
| 15 | Akinyi forgets her password | `resetMemberPasswordAction` | ⚠️ Refused because she is in another group too; she must call support, and support can only reset it (section 5). |

**Fix for the flow (summary):** an **Invite** step replaces "add member +
create login". The admin types a phone or email; if a user exists, an
invite is sent to that user (no new account, no password shared); if not,
a pending invite is stored and claimed when that phone/email registers.
Invites work while registration is incomplete, so officials can join a
private group. Section 3 is the matching identity rule.

## 3. Duplicate users

### What allows duplicates today

| Path | Why it duplicates |
|---|---|
| Register with phone only | `users.phone` has no unique constraint and `registerAction` only checks email. |
| Google sign-in | `app/api/auth/google/callback/route.ts` links by Google id, then email. A phone-only user who later taps Google becomes a second user. |
| Admin "Create login" | `createLoginForMemberAction` checks email only; a phone match silently creates a second user. An email match is a hard stop with no "link instead". |
| Add member / CSV import | `createMemberAction` and `importMembersAction` never check the roster; the same phone can be added twice, and CSV re-upload doubles everyone. |
| Join approval | `approveMembershipAction` only finds an existing `members` row by `userId`, so a roster row added by hand (no `userId`) is not linked — a second row is created. |
| Phone formats | `0712…`, `+254712…`, `254712…`, `712…` are all stored as typed. Only register and create-login validate (`^0\d{9}$`); add member, CSV and Google do not. |
| Email case | Lowercased in register/login/Google, but not in add member, CSV or create login. The unique constraint is case-sensitive. |
| Race | Register is check-then-insert; two quick submits throw a raw unique-violation error. |

Side effect: login by phone uses `findFirst` on a non-unique column, so
with two users on one phone, one of them cannot sign in by phone at all.

### Fix — one identity rule, used everywhere

1. **Normalise** in one pure function `lib/domain/identity.ts`:
   `normalizePhone("0712 345 678") → "254712345678"` (Kenya default,
   accepts `+254`, `254`, `07`, `01`, `7…`), `normalizeEmail` = trim +
   lowercase. Unit-tested.
2. **Database guarantees** (migration): unique index on `users(phone)`
   where not null; unique index on `lower(users.email)`; unique partial
   index on `members(group_id, phone)` where `active`. Before adding them,
   run the detection query below and merge.
3. **One server function** `findOrLinkPerson({ phone, email, name })` in
   a new `lib/identity/` module, used by register, Google, create login,
   invite, add member, CSV import and join approval. It returns the
   existing user if any identifier matches, links a loose roster row
   (`members.user_id is null` with the same phone in that group) instead
   of creating a new one, and only then creates.
4. **Google**: when the email is new but the user is signed in, or the
   profile email matches a member row, link; never create silently when
   a phone match exists — ask to sign in first and link from Profile.
5. **CSV import**: upsert by normalised phone (then email) within the
   group, report "12 added, 3 updated, 1 skipped (row 7: duplicate
   phone)".
6. **Merge tool** for support (super-admin → Users → Merge): moves
   memberships, members rows, sessions and notifications from the
   duplicate to the kept user, writes an audit row, deactivates the
   duplicate. Needed once for existing data.

Detection query for existing data:

```sql
select regexp_replace(phone, '^(\+?254|0)', '254') as p, array_agg(id) ids
from users where phone is not null group by 1 having count(*) > 1;
select lower(email), array_agg(id) from users where email is not null
group by 1 having count(*) > 1;
select group_id, regexp_replace(phone, '^(\+?254|0)', '254'), array_agg(id)
from members where phone is not null and active group by 1, 2 having count(*) > 1;
```

## 4. Structure and clear functions

### Problem: rules live inside UI handlers

There are ~80 Server Actions under `app/(dashboard)/dashboard/*/actions.ts`
(`mgr/actions.ts` alone is 930 lines). Each one reads the cookie session
(`requireRole`), parses `FormData`, opens a transaction, applies rules and
calls `revalidatePath`. Because the "who is acting" part is the browser
cookie, nothing else — the public API, a cron job, support, an agent — can
call them. So logic gets copied, and copies drift.

**Proven drift — recording a contribution:**

| | UI `recordContributionAction` | API `POST /api/v1/contributions` |
|---|---|---|
| Welfare contribution feeds the welfare fund | ✅ yes | ❌ no — balance silently lost |
| Balance update | atomic `col + amount` | read-then-write (lost update under concurrency) |
| Checks the member is in this group | ❌ no | ✅ yes |
| Fires `contribution.recorded` webhook | ❌ no | ✅ yes |

The route's own comment says the duplication is deliberate. It has
already produced three bugs; it should go.

### Fix: a command layer

```
lib/commands/
  types.ts          Actor, CommandResult, defineCommand()
  members.ts        inviteMember, addMember, changeRole, removeMember, …
  contributions.ts  recordContribution
  loans.ts          applyForLoan, reviewApplication, recordRepayment, …
  mgr.ts, welfare.ts, meetings.ts, fines.ts, settings.ts
  registry.ts       name → command (for the API, support console, agent)
```

```ts
type Actor = {
  userId: number;          // who the change is attributed to
  groupId: number;
  role: MembershipRole;    // effective role in this group
  via: "ui" | "api" | "cron" | "support" | "agent";
  onBehalfOf?: number;     // support/agent acting for this user
  reason?: string;         // required when via is support/agent
};

defineCommand({
  name: "contributions.record",
  roles: ["admin", "treasurer"],
  input: recordContributionSchema,        // existing zod schema
  run: async (tx, actor, input) => { … }, // today's action body, moved
  events: ["contribution.recorded"],      // webhook + notification
});
```

- `runCommand(actor, name, input)` does in one place: role check, zod
  parse, `withTenant`, the rule, an **audit row**, webhooks,
  notifications. One code path for every caller.
- A Server Action becomes three lines: build the Actor from the session,
  call `runCommand`, `revalidatePath`. The API route becomes the same with
  an API-key Actor.
- New table `group_audit_log (group_id, command, actor_user_id, via,
  on_behalf_of, reason, input jsonb, result, created_at)`, append-only like
  `mgr_slot_events`. This is also the "who did what" history admins need.
- Every command gets a `dryRun` mode (run inside a transaction and roll
  back) — needed for the agent and handy for previews.
- Move `createOnboardingGroupAction` out of `app/super-admin/` into
  `lib/commands/groups.ts`.

Do it feature by feature, starting with contributions (it has the drift).

## 5. Support access and a backend agent that can run a group

### Today

- `/super-admin/groups/[id]` is **read-only**; no actions.
- Support's only lever inside a group is `resetUserPasswordAction`, which
  replaces the user's password and signs them out everywhere — a poor way
  to "see what the user sees", and it hands support the password.
- No audit of who changed what inside a group.

### Proposal: "Act as" (support session), on top of the command layer

1. **Enter a group as support**: super-admin → group → *Open as support*.
   Creates a `support_sessions` row (`staff_user_id`, `group_id`,
   `as_user_id` nullable, `reason`, `mode` = `view` | `act`, `expires_at`
   30 min). The normal session gets `support_session_id`.
2. `getSession()` returns an extra `support` field; the Actor becomes
   `{ via: "support", userId: staff, onBehalfOf: as_user_id, role: … }`.
   Pages render exactly as that user/role sees them.
3. **A red banner on every page**: "Support mode — acting as Wanjiku
   (admin) for: *member cannot apply for loan* — ends 14:32 — Exit".
4. **View mode is the default**; `act` mode needs a reason, an owner-role
   platform user for money-moving commands (disburse, mark MGR paid,
   welfare payout), and is always audited with `via: "support"`.
5. **Never allowed in support mode**: changing passwords, Google links,
   platform roles, API keys; viewing KYC documents unless needed.
6. The group's own admins see support actions in their audit log and get a
   notification "Support changed X on your behalf".
7. This replaces password reset as the help tool; reset stays for real
   lock-outs.

### The agent

The backend agent is a **platform service user** (`platformRole =
"support"`, `kind = "agent"`) that calls `runCommand` through one internal
endpoint, `POST /api/internal/commands`, with:

- a scoped token per group (like `api_keys`, but issued by the platform),
- `dryRun: true` first, showing the plan to a human, then the real run,
- the same role checks, rules, audit and webhooks as a human — it cannot
  do anything a user with that role could not do in the UI,
- money-moving commands always require a human confirmation (maker–
  checker), the agent only prepares them.

Because the agent only calls named commands with validated input, its
behaviour is **deterministic and replayable**: the audit log is the full
record of what it did.

## 6. Deterministic in-app assistant

### Today

`lib/domain/insights.ts` → `generateRecommendations()` is already pure and
deterministic (same records in → same advice out), sorted by severity, and
unit-tested. Gaps: it has no action buttons, it only shows on
`/dashboard/insights`, it is staff-oriented, and it does not cover setup.

### Proposal: "Next steps" — rules, not a language model

1. Extend `Recommendation` with `action?: { label; href } | { label;
   command; input }` and `audience: MembershipRole[]`.
2. Add a **setup checklist** rule set for new groups: add officials →
   set contribution amount → add rules → first meeting → turn on products
   → make public. Each item links to the exact screen.
3. Add **member rules**: "Your loan application is waiting for 1
   guarantor", "Choose your Mzunguko turn by Friday", "You have a fine of
   Ksh 200", "Your KYC is missing a photo".
4. Show the top 3 on **Home** for every role; the full list stays on
   Insights.
5. Optional later: a free-text box ("record 500 for Akinyi") that uses an
   LLM **only to fill in a typed command**, which is then shown as a
   confirmation card and run through `runCommand`. The model never
   decides anything about money; rules and the user do.

Every rule is a pure function with a test, so advice is explainable
("because Akinyi's loan is 12 days past due") and never random.

## 8. Suggested order

1. **Quick fixes (1 PR):** lockfile, `/discover` dynamic, self-approval
   block on loans, member check on contributions, "My Loan" for officials,
   UTC dates, Secretary tile.
2. **Identity (1–2 PRs):** `normalizePhone`/`normalizeEmail`,
   `findOrLinkPerson`, detection + merge tool, then unique indexes.
3. **Invites:** replace "add member + create login" with Invite; allow it
   before registration is complete. Unblocks the new-group flow.
4. **Command layer + audit log:** start with contributions (fixes the API
   drift), then members, loans, MGR, welfare.
5. **Support "Act as"** on top of commands + audit.
6. **Next steps assistant** on Home (setup checklist first).
7. **Agent endpoint** with dry-run and maker–checker for money.
